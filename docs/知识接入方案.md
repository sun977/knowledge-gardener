# 灵猫知识库 · 园丁"知识接纳（Intake）"能力方案

> 版本：v2 ｜ 日期：2026-09-18 ｜ 状态：需求已确认（v1 评审后修订，未动园丁技能任何内容）
> 需求：用户把新知识链接给园丁，园丁解析理解、提出归档提案，**人同意后才执行**实体入库与索引登记。
> 关联：lingcat-knowledge-gardener skill、索引C（2787258250）、00 维护规则（2781633447）、[05]待人工审核（2781426045）

## 〇、已确认的三条决策（2026-09-18 与用户确认，后续章节以此为前提）

1. **实体入库**：新知识必须以文档实体形式进入知识库（学城来源复制入库），不做"只登记索引、实体留在原地"的外链模式。当前来源为**学城链接**；**任意网页链接是后续规划（P2）**。
2. **先提案、人同意再干活**：路由决策的产物是归档提案，园丁在获得人工确认前不执行任何入库动作。
3. **落位目标是业务目录**：接入的知识是业务知识，落入 **01-05**（实际主要是 **05 领域知识库**，且可能是**多级目录**）。**06 是 Agent 自留地，不承接外部知识**。

## 一、现状与差距

园丁目前的全部入口都是"**内向**"的：任务结束写学习日志、踩坑写记录、经验/建议/转正申请，外加巡检和已审批内容迁移。它没有"**外向 intake**"入口——外部进来一篇新知识，没有标准流程判断：

1. 这篇知识属于哪个目录（01-05 哪个领域、05 下面哪一级子目录）；
2. 该独立成篇、合并进既有文档、还是填进某个占位文档；
3. 入库动作如何取得人工确认。

对应**路由决策、落位编排、权限护栏**三个缺口。

## 二、核心任务：本质上就两件事

```
任务1  解析理解：读链接 → 判断该放哪个目录 → 输出归档提案 → 【停下，等人】
任务2  确认后执行：实体入库 → 三步走登记（改C → 渲染A/B → 变更日志）
```

其余环节（提案格式、确认闸门、留痕）不是独立任务，是包在这两个核心动作外面的护栏。完整流水线：

```
用户发链接
   ↓ ① 读取
学城来源：citadel 读取文档 + 元信息（密级/作者/更新时间）
（P2 网页来源：web_fetch 抓取正文，无密级元信息，见第五章）
   ↓ ② 理解
提取：主题、知识类型（SOP/规范/领域知识/经验）、成熟度、与现有库的重叠度
   ↓ ③ 路由（核心决策，见第三章）
与索引C 匹配（path 支持多级目录）→ 目标目录 + 落位模式 + 置信度
   ↓ ④ 提案
归档提案：目标位置 / 落位模式 / 理由 / 需确认项（含是否需新建子目录）
   ── 到此停下，低置信度必须升级人工，不允许猜 ──
   ↓ ⑤ 人工确认（对话内同意）
   ↓ ⑥ 执行
实体入库（学城 copyFrom 复制；网页来源提炼新建）→ 三步走登记
   ↓ ⑦ 留痕
学习日志记一条 intake 记录；巡检 C1/C2 兜底（漏登记/路径失配会被抓）
```

## 三、落位路由：四种模式

路由依据是**索引C 的既有元数据**（keywords / query_hint / path / summary / 各目录 purpose），不需要新建匹配语料。path 为全路径（schema v2.0），天然支持 05 下的多级目录匹配。

| 模式 | 触发条件 | 动作 | 权限 |
|------|---------|------|------|
| M1 独立成篇 | 主题独立，库内无承接文档 | 学城来源：copyFrom 复制挂载到目标目录；网页来源(P2)：提炼重写后新建。三步走登记 | 人确认后执行 |
| M2 合并入既有文档 | 与某既有文档主题重叠 | 提炼增量要点，确认后合并入目标文档（复用 migrate_to_business 的 diff 确认机制），三步走登记 | 人确认后执行 |
| M3 填占位转正 | 命中某 placeholder 文档主题（如 05 占位 SOP） | 内容填入占位文档，status 转 active、weight 回升、三步走登记 | 人确认后执行 |
| M4 暂缓/拒绝 | 密级不符 / 与红线冲突 / 内容是草稿未成熟 | 给出原因与补齐建议，不入库 | 园丁直接判定，反馈用户 |

两条不变的原则：

- **占位优先（I6 已定）**：先看能否填占位，再看合并，最后才独立成篇，抑制文档数量膨胀。每命中一次 M3 就清一笔技术债。
- **低置信度必升级**：路由输出 top-3 候选与置信度，低于阈值时必须把候选摆给人选，不允许园丁自己猜。

**多级目录的处理**：提案中的目标位置精确到全路径（如 `05 领域知识库 / 反作弊 / SOP`）。若现有目录树无合适子目录，提案中显式列出"新建子目录"动作（目录名 + 理由），与文档入库一并确认；新建目录同样登记索引C。

## 四、权限护栏

- **园丁可自主**：读取任何文档、路由分析、生成提案、M4 拒绝并反馈、写学习日志留痕。
- **必须人工确认后才执行**：一切入库动作（M1/M2/M3），因为落位目标全部在 01-05 业务目录。
- **确认形态**：对话内确认（用户回复同意提案）即视为授权，园丁随后执行；全部执行动作走三步走登记 + 学习日志留痕，保证可审计、可回溯。
- **⚠️ 制度配套（P1 前置任务）**：intake 在 `migrate_to_business.py` 之外新增了**第二条业务目录写入入口**。实现时必须把该入口明文写进 00 维护规则和 `references/kb-structure.md` 的权限矩阵，不允许只存在于本方案中——规矩可以改，但不能只破不立。
- **源文档处置**：一律**复制入库**（createDocument --copyFrom），源文档留在原作者空间不动（Never break userspace）。不做 moveDocument。

## 五、来源抽象：学城 vs 任意网页（P2 规划）

流水线对来源做抽象：**①读取 和 ⑥入库 两步按来源分派，中间的 ②理解 / ③路由 / ④提案 完全一致**。

| 维度 | 学城链接（当前） | 任意网页链接（P2 规划） |
|------|----------------|----------------------|
| 读取方式 | citadel getDocumentXml / 元信息接口 | web_fetch / 浏览器抓取正文 |
| 密级元信息 | 有，M4 硬规则可自动判定 | 无，需人工判断来源可信度与合规性 |
| 实体入库方式 | copyFrom 原样复制 | 无法复制，必须**提炼重写**为知识库格式后新建 |
| 主要风险 | 密级高于库密级 | 内容质量参差、版权/合规、广告噪音混入 |

设计含义：当前只实现学城分支，但在提案和登记的数据结构上预留 `source_type` 字段（km / web），避免 P2 时返工。

## 六、与现有组件的复用关系（几乎不造新轮子）

| 现有组件 | 在 intake 中的角色 |
|---------|------------------|
| 索引C 元数据 | 路由匹配的语料（keywords/query_hint/path/summary/purpose） |
| 三步走（经验沉淀已固化） | 所有登记动作的统一路径（改C → 渲染A/B → 变更日志） |
| migrate_to_business.py 的 diff 确认机制 | M2 合并时复用 |
| health_check C1/C2（R5） | 兜底：挂载漏登记 → 悬挂节点；登记路径错 → path 失配 |
| 学习日志 | 每次 intake 留痕 |

**唯一需要新增的**：`intake_knowledge.py`（P1 阶段）——**边界必须钉死**：脚本只做机械活（新链接 contentId 去重检查、密级比对、提案文案模板渲染），**语义路由和置信度判断是 Agent 的活，不进脚本**。延续"脚本纯计算、Agent 指挥、citadel 执行"的架构约定。
